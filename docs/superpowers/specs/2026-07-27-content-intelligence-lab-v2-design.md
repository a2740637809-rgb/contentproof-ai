# AI 内容洞察实验室 V2 产品规格

日期：2026-07-27  
状态：产品方向已确认，等待书面规格复核  
范围：只定义产品问题、用户流程、MVP 边界和验收标准，不包含技术实现计划

## 1. 产品定位

### 1.1 名称

- 英文暂定名：Content Intelligence Lab
- 中文暂定名：AI 内容洞察实验室

### 1.2 目标用户

第一版服务个人内容运营、媒体编辑和公众号作者。用户需要从公开文章评论中寻找后续选题，但没有时间逐条阅读和整理大量反馈。

第一版不针对专业研究团队、产品经理、客服团队或多人协作组织。

### 1.3 用户问题

文章评论中包含读者的疑问、误解、担忧和新需求。现有处理方式存在三个问题：

1. 人工逐条阅读效率低；
2. 普通 AI 总结容易脱离原文；
3. 总结结果难以直接转化为下一篇内容的行动方案。

### 1.4 价值主张

产品帮助用户从公开文章和评论中发现读者真正关心的问题，并生成每项判断都有原始评论支撑的图文内容 Brief。

一句话定义：

> 把一篇文章下面大量、杂乱的读者评论自动整理成几个有原文证据的真实需求，再帮助内容运营人员决定下一篇文章应该写什么、怎么写。

## 2. 已确认的产品决策

| 决策项 | 第一版选择 |
|---|---|
| 主要输出 | 公众号或新闻客户端图文内容 Brief |
| 主要数据 | 公开文章正文和读者评论 |
| 核心用户 | 单人内容运营或编辑 |
| 数据入口 | 公开链接抓取，粘贴与 CSV/XLSX 上传兜底 |
| AI 运行方式 | 本地模型优先 |
| 产品方法 | AI 自动发现候选主题，用户人工确认 |
| 核心差异 | 每条洞察均可追溯至原始评论 |

## 3. 核心任务闭环

```text
创建研究任务
      ↓
导入文章与评论
      ↓
检查和清洗数据
      ↓
AI 发现候选主题
      ↓
人工审阅原始证据
      ↓
生成、编辑并导出内容 Brief
```

### 3.1 创建研究任务

用户必须先填写研究目标，例如：

> 分析端午禁毒宣传报道的读者评论，寻找下一篇解释型报道的选题。

研究目标用于约束后续主题解释和 Brief 生成，避免出现与任务无关的泛化总结。

### 3.2 导入文章和评论

支持以下入口：

1. 输入公开文章链接；
2. 直接粘贴评论；
3. 上传 CSV 或 XLSX 文件。

链接导入尝试获取：

- 标题；
- 正文；
- 作者；
- 发布时间；
- 当前页面公开可访问的评论。

系统不得承诺抓取所有网站或所有评论。每次抓取结束后必须分别说明正文和评论的获取状态、数量、缺失内容、失败原因及替代导入方式。

### 3.3 检查和清洗数据

系统识别：

- 重复评论；
- 广告和无意义内容；
- 只有表情或信息不足的短评；
- 手机号、邮箱等个人信息；
- 内容不完整的数据。

被过滤的数据进入“待排除区”，用户可以查看和恢复。第一版不自动永久删除原始导入内容。

### 3.4 发现候选主题

分析顺序：

```text
评论文本
   ↓
本地 Embedding 模型生成语义向量
   ↓
聚类算法形成候选评论组
   ↓
本地 LLM 为评论组命名并解释
```

Embedding 只负责表达语义相似度；聚类算法负责分组；本地 LLM 负责生成便于人理解的主题名称和解释。第一版不为了技术展示强制引入独立向量数据库。

### 3.5 人工审阅洞察

每个候选主题显示：

- 主题名称；
- 评论数量；
- 代表性原始评论；
- 分组依据；
- 审核状态。

用户可以：

- 修改主题名称；
- 合并重复主题；
- 拆分混乱主题；
- 在主题之间移动评论；
- 驳回无价值主题；
- 确认可用于内容策划的主题。

所有 AI 主题默认处于“待确认”状态。未经确认的主题不得进入最终 Brief。

### 3.6 生成内容 Brief

系统只使用已确认主题，生成：

- 建议选题；
- 目标读者；
- 读者核心问题；
- 推荐内容角度；
- 文章结构；
- 必须回答的问题；
- 原始评论证据；
- 事实与表达风险提示。

Brief 中的证据可以返回对应原始评论。用户可以编辑内容，并导出 Markdown 或 Word 文件。

## 4. 页面结构

### 4.1 项目首页

职责：创建和管理研究任务。

主要信息：

- 项目名称；
- 分析进度；
- 评论数量；
- 最后修改时间。

真实操作：

- 新建研究；
- 继续分析；
- 删除项目；
- 打开示例项目。

### 4.2 数据导入页

职责：导入公开文章和评论。

真实操作：

- 开始抓取；
- 上传文件；
- 粘贴评论；
- 预览数据；
- 确认导入。

### 4.3 数据检查页

职责：在 AI 分析前确认数据质量。

真实操作：

- 排除；
- 恢复；
- 批量确认；
- 开始分析。

### 4.4 洞察审阅页

职责：检查 AI 分组并完成人工判断。

布局原则：

- 左侧：评论与筛选；
- 中部：候选主题；
- 右侧：证据、解释和审核操作。

真实操作：

- 重命名；
- 合并；
- 拆分；
- 移动评论；
- 驳回；
- 确认；
- 重新分析。

二维洞察地图只可作为后续探索视图，不作为第一版主要决策界面，也不用于证明主题重要性。

### 4.5 Brief 工作台

职责：把确认后的读者需求转化为写作方案。

真实操作：

- 生成 Brief；
- 重新生成单个部分；
- 查看证据；
- 编辑；
- 导出 Markdown；
- 导出 Word。

## 5. 异常与降级

### 5.1 网页抓取失败

- 保留已成功获取的部分；
- 显示具体失败步骤；
- 不将“正文成功”误报为“评论成功”；
- 提供粘贴和文件上传入口。

### 5.2 本地模型不可用

- 检查 Ollama 服务和所需模型；
- 告知用户缺少的依赖和恢复方法；
- 不伪造 AI 分析结果；
- 已导入和已清洗的数据不得丢失。

### 5.3 聚类质量不足

- 显示未归类评论；
- 允许调整候选主题数量或重新运行；
- 允许用户完全通过人工方式整理；
- 不使用没有定义来源的“综合质量分”掩盖失败。

### 5.4 生成失败

- 保留已经确认的主题和人工修改；
- 只重试失败步骤；
- 不重复执行已完成的抓取、清洗和审核。

## 6. 第一版范围

### 6.1 必须完成

- 研究项目持久化；
- 公开链接抓取；
- 评论粘贴；
- CSV/XLSX 上传；
- 数据去重、过滤、脱敏和恢复；
- 本地 Embedding；
- 评论语义聚类；
- 本地 LLM 主题解释；
- 主题重命名、合并、拆分、移动、驳回和确认；
- 证据化 Brief；
- Markdown 和 Word 导出；
- 关键操作记录；
- 示例数据和完整演示流程。

### 6.2 明确不做

- 多人协作；
- 账号与复杂权限；
- 自动发布；
- 实时全网舆情监控；
- 所有平台的自动评论抓取；
- 付费系统；
- 历史文章 RAG；
- Prompt 实验中心；
- 阅读量增长预测。

## 7. 后续阶段

### 第二阶段：AI 实验中心

使用固定测试集，对比不同模型、Prompt 和聚类方法。记录真实准确率、错误分组、人工修改次数、运行时间和失败案例。

### 第三阶段：历史内容知识库

加入 RAG，用于查询历史文章是否覆盖相似问题、寻找可引用材料和识别内容空白。不得在缺少曝光、点击和对照数据时推断阅读量高低的原因。

### 第四阶段：发布效果复盘

由用户录入阅读量、点击率、完读率、评论数量等真实发布数据，比较选题判断与实际反馈。

## 8. 验收标准

第一版必须同时满足：

1. 新用户能在 10 分钟内完成一次评论分析；
2. 支持公开链接、粘贴、CSV/XLSX 三类数据入口；
3. 抓取失败时显示原因和替代方案；
4. 每条洞察都能查看对应原始评论；
5. 用户可以修改、合并、拆分和驳回 AI 主题；
6. 只有确认后的主题可以生成 Brief；
7. 关闭并重新打开后，项目数据仍然存在；
8. 所有主要按钮都具有真实行为；
9. 不显示装饰性分数或虚构业务成果；
10. 可以完全使用本地模型运行；
11. Brief 可以导出并继续用于真实写作；
12. 自动化测试覆盖主流程和主要失败路径。

## 9. 名词解释

| 名词 | 简明解释 |
|---|---|
| Brief | 写作前的内容策划简报，不是完整文章 |
| Firecrawl | 从公开网页提取标题、正文和链接等内容的工具 |
| 数据清洗 | 去重、过滤无效内容、统一格式并隐藏个人信息 |
| Embedding／语义向量 | 把文字转换成可以比较语义距离的一组数字 |
| 语义聚类 | 按照意思而非完全相同的词语对评论自动分组 |
| 本地模型 | 直接在用户电脑上运行、不默认上传数据的 AI 模型 |
| Ollama | 在个人电脑上下载和运行大语言模型的工具 |
| Qwen | 通义千问系列模型，项目使用其本地可运行版本 |
| LLM | 能理解和生成自然语言的大语言模型 |
| Markdown | 可保留标题、列表和引用的轻量文本格式 |
| RAG | AI 回答前先从指定资料库检索相关内容的方法 |
| Prompt | 发送给 AI 的任务说明和约束 |
| 聚类算法 | 按相似程度把数据自动分组的计算方法 |

## 10. 参考产品及借鉴边界

- [Dovetail](https://dovetail.com/)：借鉴“AI 分析必须以证据为基础”的定位，不复制其企业级客户智能平台范围。
- [Taguette](https://github.com/remram44/taguette)：借鉴原文高亮、人工标签和可导出研究结果，不复制完整质性研究软件。
- [Dify](https://github.com/langgenius/dify)：借鉴可观察、可恢复的 AI 工作流，不引入通用 Agent 编排平台。
- [Langfuse](https://github.com/langfuse/langfuse)：后续借鉴数据集、实验和评测闭环，不在第一版实现完整 LLM 工程平台。

## 11. 产品原则

1. 先证据，后结论；
2. AI 提建议，人做最终判断；
3. 失败必须可见，不用假数据美化；
4. 先完成单人内容运营的核心闭环，再扩展其他场景；
5. 技术只在解决用户问题时加入，不为了堆砌名词而加入。
